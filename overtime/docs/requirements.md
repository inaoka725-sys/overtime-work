## 1. 背景と目的

### 目的（重みの順。2026-11-26 発注者）
1. **事務スタッフの業務軽減**（当初より重みが大きくなった）
2. 現場社員の利便性（スマホで日報、紙の押印・提出をなくす）

### 事務の現状の困りごと
- 年間勤務表は数式が複雑で何年も使っており、壊れている恐れがある（実際に [a] の AA 列が Y 列（31日の右半分）を見ない
  集計漏れ・超勤年間が「前月迄（手入力）＋当月の徹夜回数」で時間を足していない誤りを確認済み）。手入力・転記のミスも含みうる → 日報から合計欄を自動計算し、手入力・転記を無くす（§9-2）
- 旬報・残業の提出が、特に出張中などに遅れる社員がいる。事務がいちいちサーバーの個人フォルダを見に行っていた
  → 提出状況の一覧（§3-4）。スマホ入力で出張中も提出できる
- 給与ソフト CCS へは1人ずつ画面で手入力している → 同じ並びの転記表を出す（§9-3）

### 経緯
- 2026-11-20: 事務スタッフの現行帳票・作業フローを踏まえて作り直す方針（稲岡さん決定）
- 2026-11-25: 事務スタッフ打合せ。計算ルール確認シート10項目（平日残業開始＝開始＋9h30m、休憩7帯、普通/深夜の境、休出、深夜作業手当、帰社後作業、30分単位、日またぎ、日当、交通費・宿泊費・手当列）が全項目「問題なし」
- 2026-11-26: 稲岡さんと本書の内容を決定。発注者から目的の重み・提出状況一覧・CCS 対応の追加要望

### 成果目標
社員が毎日1回入力するだけで、上長の承認・事務の確認を経て、工事原価と給与計算に必要な数字がそろう。
事務は個人フォルダを見に行かず、転記もせずに旬・月を締められる。

### 成功指標
- 事務の手入力（年間勤務表・給与ソフトへの転記・オーダ別表）をなくす、または大きく減らす
- 事務が提出状況の確認のために個人フォルダを見に行かなくてよい
- 残業時間・深夜作業手当の計算ミスゼロ（規程どおりの自動計算）
- 紙の押印・提出をなくす（上長は外出先からも承認できる）

### クラウド利用の範囲（2026-11-26 稲岡さん明言）
外部クラウドに置かないのは**顧客との守秘義務情報（見積書・図面など）だけ**。勤怠・経費はクラウドに置いてよい。
現行版の「元請けからクラウド禁止」という記述はこの意味に正す。オーダー台帳ファイル自体は外に出さず、
アプリに必要な4項目（オーダー番号・件名・担当者・日当）だけをクラウドへ反映する（§10）。

## 3. 画面

### 3-1. タブごとの「誰が・何を・どう見るか」

| タブ | 誰が | 何を | どう見る・どう操作する |
|---|---|---|---|
| 日報入力 | 全員 | 自分の1日の勤務結果 | 1日ずつ入力。残業・深夜作業手当はその場で計算して表示。残業があるときは上長を選ぶ。スマホで入力できる |
| 〃（事務の全員分表示） | 事務・管理者 | 提出状況の一覧（§3-4）・個別明細 | 社員を選んで明細を開き修正（履歴は §13 #11） |
| 残業報告 | 社員＝自分 | 年月・旬ごとの残業の集計 | 各行に「仮（承認待ち）／承認済み／差し戻し」を表示。行から日報を開いて修正 |
| 〃（承認） | 上長 | 自分宛の承認待ちの残業 | 旬・社員ごとにまとめて表示。1件ずつ／まとめて承認、理由を付けて差し戻し。スマホで操作できる |
| 〃（事務の全員分表示） | 事務・管理者 | 全員分の残業 | 「残業一覧」（Excel・CSV）と「給与計算（CCS 転記表）」（CCS 転記表・年間勤務表の合計欄。画面・Excel・CSV）（§9） |
| 旬報 | 社員＝自分 / 事務＝全員 | 年月・旬ごとの経費（日当・交通費など）とオーダー別集計 | 社員は自分の経費とオーダー別（労務原価なし）を見るだけ。事務の全員分表示で工事原価（全員一括か1人）と旬報 Excel を出力 |
| 設定（管理者用） | 事務・管理者だけ | 本人情報・マスター類 | オーダーマスター・台帳連携（§10）、旬〆、社員情報、労務原価の単価、役割の付与（管理者）。**社員・上長にはタブを出さず、URL で開いても日報入力へ戻す**（2026-11-27 稲岡さん）。狭い画面のタブ名は「管理者用」 |

- 社員の本人情報（氏名・社員番号・所属）と「パスワードの変更は設備予約アプリで」の案内（§14-1）は、日報入力タブの本人の行に出す

### 3-2. 日報の入力項目

| 項目 | 内容 |
|---|---|
| 日付 | 必須。今日を初期値 |
| 勤務区分 | 必須。常用 / 休出 / 有給 / 代休 / 欠勤。徹夜は常用・休出の行に付ける印（§13 #1・#26） |
| 区分 | 現場作業 / 社内作業 |
| オーダー番号 | クラウドのオーダー一覧から選ぶ・打つ。件名・担当者・日当を自動補完。一覧に無い番号は §10-4 |
| 作業開始・終了 | 30分刻み。常用・休出は必須。日またぎ可 |
| 帰社後作業 | 現場作業のときだけ。開始・終了・オーダー番号・件名 |
| 上長 | 残業（普通・深夜）または深夜作業手当が出る日は必須（深夜作業手当も承認の対象にするのは推奨案）。前回選んだ人を初期値 |
| 日当 | オーダーの値で自動補完（変更可） |
| 交通費 | 利用機関・出発・到着・片/往・片道金額（原本の列）。交通費＝片道金額、往復は×2 |
| 備考 | 任意 |

- **遅刻・早退は管理しない**（業務に影響しない遅出・早退は黙認。2026-11-27 社長）。入力項目に持たず、常用の出勤扱い
- **社内残業＝現場から事務所に戻ってからの作業＝「帰社後作業」**（2026-11-27 事務）。別の入力欄は作らない
- 宿泊費は会社が予約・精算するため社員の入力欄は設けない（推奨）。旬報の宿泊費・手当の列は事務が必要に応じ記入（§13 #5）
- 1日に複数行（オーダーの違う作業）を入れられる。同じ人・同じ日・同じ開始時刻は重複として拒否
- **同じ日の複数行はまとめて計算する**（2026-11-27 稲岡さん決定。§6「同じ日の複数行」）。同じ社員の他の行と作業時間
  （帰社後作業を含む）が実際の時刻で重なる行は保存できない（日付が違っても。重なった時間を二重に数えるため。画面と DB
  の両方で拒否）。入力画面には同じ勤務日の他の行と合わせた計算であることと、その日の合計を出す
- 夜をまたぐ作業を0時で分けるときは、0時からの行を**翌日の日付**で入れる（前日の続きとしてまとめて計算する。§6 勤務日）。
  同じ日付のまま 00:00〜 と入れた行が、同じ日の別の行の終了（24:00 など）とつながって見える場合は保存せず、「翌日の
  日付で入れる／1行で入れる」よう案内する（そのままではその日の朝の作業として計算され、残業開始が早まるため）
- 入力チェックは現行版と同じ（開始＝終了の拒否、帰社後開始は本作業の終了以降、帰社後が6時間超あくときの確認、金額のマイナス不可）

### 3-3. 画面の共通事項
- PC（幅1366）とスマホ（幅390）の両方で使える
- 現場（外出先）から日報・残業を入力でき、上長も外出先から承認できる
- 一覧の最新化は、画面を開いた時・画面に戻った時・保存した時と「更新」ボタン（短い間隔の自動読み込みはしない。§11）

### 3-4. 提出状況の一覧（事務・管理者。必須）
- 旬ごと・社員ごとに、状態を **未入力日あり ／ 提出済み ／ 承認待ち ／ 承認済み** で表示する
  - 未入力日あり: その旬の勤務日に日報が1行も無い日がある（日付も表示）
  - 提出済み: 全勤務日の日報があり、承認の要る行（残業・深夜作業手当）が無い
  - 承認待ち: 承認待ち・差し戻しの残業がある（上長名も表示）
  - 承認済み: 全勤務日の日報があり、承認の要る行がすべて承認済み
- 期限（原紙の「各旬報〆日から3営業日以内」）を過ぎて未入力日あり・承認待ちのものを**強調**する
- 勤務日・会社の休日は**予定表（gansuke）に登録された会社の休日**で判定する（読むだけ。登録は社長。§13 #2）。本人への督促通知（メール等）の要否は §13 #13

## 5. 承認の状態遷移（残業）

```
（日報を保存）
   ├─ 残業・深夜作業手当が無い日 ……………… 対象外（承認不要）
   └─ ある日 ……………………………………… 承認待ち（＝仮）
                                              │ 上長が承認
                                              ├────────→ 承認済み（＝本登録）
                                              │ 上長が差し戻し（理由必須）
                                              └────────→ 差し戻し ─（社員が直して保存）→ 承認待ち
```

- 承認は**上長の1段だけ**。原紙の提出経路「直近上司→所属部長→事務」の**所属部長は承認経路から外れる**（§13 #10）
- 給与計算の出力は**承認済みだけ**を数える。承認待ち・差し戻しが残っていれば出力画面に件数と氏名を出す
- 承認待ちの間は本人が修正・削除できる。承認済みを直した場合・旬〆後のロックは §13 #9・#12
- **承認は日単位**（2026-11-27 稲岡さん決定。日は §6 の勤務日）: 承認が要るのは、その日（同じ社員・同じ勤務日・同じ勤務区分）のどれかの行に
  残業・深夜作業手当がある日の、作業時間のある**すべての行**（朝の行の開始がその日の残業開始を決めるため、残業が
  割り振られない行も上長が確かめる）。給与計算に数えるのは承認済みの行に割り振られた分だけ
- **同じ日の他の行の承認の揃え方**（DB が保存のたびに行う。junpo 0011）:
  - その日に承認が要るようになった → 承認不要だった同じ日の行も承認待ち（上長は保存した行で選んだ上長）
  - **本人がその日の作業時間（日付・勤務区分・開始・終了・帰社後の時刻）を変えた・行を足した・消した** → 同じ日の
    承認済み・差し戻しの行も承認待ちに戻す（§13 #9「本人が直すと承認待ちに戻る」を日に広げたもの）。作業時間以外
    （交通費・備考など）だけの修正では、同じ日の他の行は変わらない
  - 保存した行が承認待ちなら、同じ日の承認待ちの行の上長もその上長に揃える（上長の選び直しも同じ日の承認待ちに及ぶ）
  - その日に残業・深夜作業手当が無くなった → 承認待ちの行は承認不要に戻す（本人の作業時間の変更なら承認済みも）
  - 事務・管理者が他人の行を直したときは、同じ日の承認済み・差し戻しの行はそのまま（§13 #9「事務の修正は承認済みのまま」）
  - 揃えるのは保存後の勤務日・元の勤務日（日付や時刻を変えた・消した）と、勤務日が変わる続きの行（前日の続きでなく
    なる・続きになる行）の勤務日。入力画面は、承認待ちに戻る日（元の日と新しい日の両方）を案内する（junpo 0012）
  - 上長は、自分が上長に選ばれている行と同じ勤務日の行（日付をまたぐ続きの行を含む）と、同じ日付の行を読める（その日の
    行と合わせて計算して確かめるため）
  - 同じ社員の日報を本人と事務が同時に保存しても取り違えないよう、日報の書き込みは DB が順番に処理する
- 承認した人・日時、差し戻しの理由を記録する
- 上長本人の残業は**本人が承認者でよい**（上長は年俸制で残業の対象外のため。2026-11-26 決定）
- 上長が不在のときは、**社員が上長を別の人に選び直す**。管理者の代理承認は設けない（2026-11-26 稲岡さん決定）

## 6. 規程ルール（変更しない）

出典: `時間外手当基準（原紙）.xlsx`。確認シート（2026-11-25）で全項目確定。原紙内の残業開始の食い違いは **＋9時間30分** で確定扱い。

### 残業開始
- 常用（平日）: 勤務開始 ＋ **570分（9時間30分）** ← 絶対に変えない（例: 9:00→18:30、8:00→17:30、12:00→21:30）
- 休出（休日）: 勤務開始から全時間
- 有給・代休: 残業計算なし

### 休憩帯（7種）
08:30-09:00 / 12:00-13:00 / 15:00-15:30 / 18:00-18:30 / 22:00-22:30 / 02:00-03:00 / 06:00-06:30

### 時間外手当
| 種別 | 内容 |
|---|---|
| 普通残業(H) | 残業 ∩ [6:00-22:00] の実働時間（休憩除く） |
| 深夜残業(H) | 残業 ∩ [22:00-翌6:00] の実働時間（開始日の 0:00-6:00 も深夜帯） |
| 深夜作業手当 | 常用勤務の [勤務開始, min(残業開始, 勤務終了)] ∩ [18:00-翌6:00] の実働が5時間以上 → **一律3,000円**。休出は常に0円 |

- 深夜作業手当と同一時間帯の時間外作業手当は重複不可
- 集計は 0.5時間単位（四捨五入）: `Math.round(分 / 30) * 0.5`
- 開始＝終了は24時間勤務と区別できないため登録を拒否

### 同じ日の複数行（2026-11-27 稲岡さん決定）
1日を複数行（オーダー違い）に分けても、1行で入れたときと同じ残業・深夜作業手当になるよう、**同じ社員・同じ勤務日
（作業開始の日付）・同じ勤務区分の行をまとめて計算する**。上の規程そのものは変えない。
- 残業開始: 常用は**その日の最初の開始**＋570分、休出は各行の開始から全時間
- 深夜作業手当: 各行の [開始, min(その日の残業開始, 終了)] ∩ [18:00-翌6:00] の実働の合計が5時間以上で、**日に1回** 3,000円
- 0.5時間単位の丸めは**日の合計**で行う。各行への割り振りは、その行の時間帯と残業が重なる分（開始の順に足した累計を
  丸めた値の差。割り振りの合計＝日の合計）。手当は判定に勤務が入った行のうち開始の最も早い行に載せる
- 例: 08:00-12:00 ＋ 13:00-翌02:00 は 1行 08:00-02:00 と同じ普通4H・深夜3.5H（残業は2行目に割り振る）。
  18:00-23:30 ＋ 23:30-翌05:00 は 1行 18:00-05:00 と同じ深夜1.5H・深夜作業手当3,000円
- 給与計算・CCS 転記表・残業一覧・残業報告・承認の画面は、すべてこの日単位の計算の割り振りを使う。1行だけの日は従来と同じ結果
- **勤務日**（2026-11-27 稲岡さん決定）: 日は行の日付（作業開始の日付）で分ける。ただし、同じ勤務区分の別の行の本作業の
  終了（24:00＝翌0:00、または日またぎの終了）と開始がちょうど一致する行（切れ目ない続き）は、その行と同じ勤務日にする。
  夜をまたぐ作業を0時で分けて翌日の日付で入れた行は前日の勤務日に入り、それに切れ目なく続く同じ日付の行（オーダー替え）
  や、続きの続き（3日の日付にまたがる）も同じ。勤務区分が違う行・少しでも間があく行はつながない
  - 例: 08:00-24:00 ＋ 翌日付 00:00-05:00 は 1行 08:00-05:00 と同じ普通4H・深夜5.5H。18:00-24:00 ＋ 翌日付 00:00-05:00 は
    1行 18:00-05:00 と同じ深夜1.5H・深夜作業手当3,000円。20:00-24:00 と 翌日付 00:00-05:00 は1行ずつなら手当なし、
    つながると手当が付き、両方の行が承認待ちになる
  - 残業・手当・日数は勤務日の月・旬に数える（例: 11/30 の夜の続きの 12/1 の行の残業は11月の給与計算・残業一覧に載る）。
    期間の集計は前後の日の行も読んで計算する。経費（日当・交通費）と、行を直せるかどうか（旬〆）は行の日付の旬のまま
  - 同じ日付のまま 00:00〜 と入れると、その日の朝の作業として計算される（08:00-24:00 ＋ 同じ日付 00:00-05:00 は
    普通10.5H・深夜1.5H）。この紛らわしい入力は画面が保存しない（§3-2）

### 帰社後作業
- 常用: 残業起点 ＝ max(帰社後作業の開始, 本作業の残業開始)
- 休出: 帰社後作業自身の開始が起点
- 帰社後の開始が本作業の開始より前なら翌日とみなす（例: 本作業 9:00-23:00 ＋ 帰社後 0:00-2:00 は翌日 0:00-2:00）

### 旬・交通費
- 一旬 1〜10日 / 二旬 11〜20日 / 三旬 21日〜末日（末日は月の実日数）
- 往復は入力金額×2

  **変わった時だけ**4項目（オーダー番号・件名・担当者・日当）をクラウドの `orders` へ反映する（現行の仕組みを流用）
- 常時開いておく必要はない。開いた時に最新化される
- 2台の PC が同じ版の台帳を二重に反映しないよう、`ledger_sync` の更新日時・サイズと照合してから反映する
- **期替わりに対応する**: 台帳は期ごとのファイル（例: 35期・36期）で、前期の番号が当期にも使われることがある。
  複数の期の台帳をつなげ、オーダーは（期, 番号）で区別する。同じ番号が複数の期にあるときは期と件名を並べて選ばせる
- **台帳から消えた番号をすぐ無効にしない**: 「台帳で最後に見た日時」を残し、無効にするのは事務が一覧で確認してから
- アプリは https で配信されるため、Chrome / Edge なら **Chrome のポリシー設定なしで** File System Access API が使える
  （台帳ファイルへの接続を事務 PC のブラウザが覚える。初回とブラウザ再起動後は「台帳に再接続」の1クリックが要る）
- **各社員の PC での台帳連携・GPO（グループポリシー）配布は不要**になる
- 手動取込（ファイルを選ぶ）も残す（連携できない時用）

### 10-2. 解析の仕様（現行の `parseOrderWorkbook` を流用）
- シート: 名前に「台帳」を含むものを優先、無ければ先頭
- 見出し行: 先頭20行以内で「ｵｰﾀﾞｰ」または「オーダー」を含む行
- 列: オーダー（必須）／件名・工事／担当／日当を自動で対応付け
- 数値セルのオーダー番号は整数の文字に直し、空・0 の行は読み飛ばす
- 見出しやデータが見つからない時は理由を表示して止める（隠さない）
- 実績: 実台帳で 2,993 件の取込を確認済み

### 10-3. 社員側
- 日報のオーダー番号から、クラウドのオーダー一覧で件名・担当者・日当を自動補完する（台帳には触れない）
- 本番は1回の読み出しが**最大1,000行**（`max_rows=1000`）で、台帳は 2,993 件ある。全件を読まず、
  **打った番号で絞り込んで必要な分だけ読む**。全件が要る処理（台帳反映の照合）は1,000件ずつ分けて読む

### 10-4. 一覧に無いオーダー番号（未確定）
- **案1（推奨）**: 社員が番号・件名を手入力して登録でき、設定タブの一覧に「未確認」と表示する。後で台帳に載れば自動で確認済みになる
- 決定は §13 #4

**Pro 化・有料オプションは行わない。上限を超えそうなら稲岡さんに相談する。**

- 品質: 関数100行以下・ファイル700行以下・行長120文字（設備予約アプリに合わせる）

## 14. 設備予約アプリとの共用で注意すること

1. **パスワードの設定・変更は設備予約アプリに統一**: 設備予約アプリの関数 `account-admin` は呼び出し元を設備予約アプリの URL だけに
   限っている。また旬報アプリ側でパスワードを変えても、名簿の「初回変更が必要」の印（`members.must_change_password`）が消えない。
   **推奨: 初期パスワードのままの人には「設備予約アプリでパスワードを設定してください」と案内して止める**（設備予約アプリには手を付けない）
2. ログインの共用: 同じ ID・パスワードで入れるが、アプリの URL が違うため、ログインはそれぞれの画面で1回ずつ必要
3. アカウントの追加・退職者の無効化・パスワードの初期化は設備予約アプリの「アカウント管理」で行う。
   無効化された人は旬報アプリにも入れなくなる
4. 名簿の表記は「白浜宗則」（打合せでは「白濱」）。画面の表示は名簿のとおりになる
5. **名簿の行の削除**: 設備予約アプリの検証手順（`account_admin.integration.ts`）は試験用の行を名簿から削除する。
   旬報アプリは名簿に外部キーを張らない（§8）ので、この手順を止めず、旬報データも消えない
